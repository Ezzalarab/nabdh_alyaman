# خارطة طريق التنفيذ التقني (Technical Roadmap)

هذا المستند يحدد مراحل التنفيذ مع قائمة مهام (Checklist) لكل مرحلة وتقدير زمني واقعي، لضمان الانتقال السلس دون أخطاء.

> **التقدير الزمني الكلي**: 6-8 أسابيع للمطوّر الفردي بدوام جزئي.

---

## المرحلة الأولى: بناء النواة وهجرة البيانات
**الهدف**: تشغيل السيرفر ونقل البيانات التاريخية من Firebase بنجاح.
**التقدير الزمني**: 2 أسبوع

### 1-أ: إعداد البيئة والبنية التحتية
- [ ] تثبيت PostgreSQL 16 وتفعيل إضافة PostGIS (محلياً للتطوير).
- [ ] إنشاء مشروع NestJS وتثبيت التبعات (راجع `backend_implementation.md`).
- [ ] ربط Prisma بـ PostgreSQL وإنشاء الجداول عبر `npx prisma migrate dev`.
- [ ] تنفيذ استعلامات PostGIS يدوياً بعد الـ migrate (إضافة عمود `coords` وإنشاء الفهرس).

### 1-ب: استيراد شجرة المواقع
- [ ] تشغيل سكربت seed لاستيراد بيانات المحافظات والمديريات من `seed_locations.md`.
- [ ] التحقق من صحة البيانات: عدد المحافظات = 22، التسلسل الهرمي صحيح.

### 1-ج: هجرة البيانات التاريخية
- [ ] تصدير Firebase JSON (donors, centers, notifications, global_app_data).
- [ ] تطوير وتشغيل سكربت `migrate.ts` (راجع `data_migration_plan.md`).
- [ ] التحقق اليدوي من 50 سجل عشوائي.
- [ ] إرسال إشعار للمستخدمين بضرورة إعادة ضبط كلمة المرور.

**علامة اكتمال المرحلة**: قاعدة البيانات تحتوي على جميع البيانات القديمة، والاستعلامات الجغرافية تعمل بشكل صحيح.

---

## المرحلة الثانية: نظام الحماية وتعدد الأدوار (Auth & RBAC)
**الهدف**: تسجيل دخول آمن وفصل صلاحيات كل دور.
**التقدير الزمني**: 1.5 أسبوع

- [ ] برمجة `POST /api/v1/auth/login` (بالهاتف + kلمة المرور).
- [ ] برمجة `POST /api/v1/auth/register` للمتبرعين.
- [ ] برمجة `POST /api/v1/auth/reset-password` لدعم مستخدمي الهجرة.
- [ ] بناء `JwtAuthGuard` و`RolesGuard` وتطبيقهما على الـ Endpoints.

**اختبار المرحلة**:
- [ ] محاولة الوصول لـ endpoint إداري بتوكن متبرع → يجب الرفض (403).
- [ ] تسجيل دخول بهاتف صحيح وكلمة مرور خاطئة → يجب الرفض (401).

---

## المرحلة الثالثة: المحرك الجغرافي والبحث (Geospatial Engine)
**الهدف**: تفعيل ميزة البحث عن أقرب المتبرعين.
**التقدير الزمني**: 1 أسبوع

- [ ] برمجة `GET /api/v1/donor-search` مع دعم فلاتر: فصيلة الدم، الموقع، المسافة.
- [ ] تطبيق خوارزمية التوسع: 5km → 10km → المديرية → المحافظة.
- [ ] التأكد من وجود فهرس GIST على عمود `coords`.

**اختبار المرحلة**:
- [ ] إدخال بيانات وهمية لمتبرعين في مواقع مختلفة.
- [ ] البحث بموقع محدد والتحقق من ترتيب النتائج تصاعدياً بالمسافة.

---

## المرحلة الرابعة: إدارة المحتوى والمخزون (Dashboard & Inventory)
**الهدف**: تمكين مراكز الدم والمشرفين من إدارة النظام.
**التقدير الزمني**: 1.5 أسبوع

- [ ] برمجة `PATCH /api/v1/centers/:id/stock` لتحديث المخزون (مع تسجيل في `StockTransaction`).
- [ ] برمجة `GET /api/v1/app-config` لجلب إعدادات التطبيق (CMS).
- [ ] برمجة `PUT /api/v1/app-config/:key` لتحديث الإعدادات (ADMIN فقط).
- [ ] ربط نظام الإشعارات: `POST /api/v1/notifications/send`.

**اختبار المرحلة**:
- [ ] تحديث مخزون مركز والتحقق من إنشاء سجل في `StockTransaction`.
- [ ] تحديث إعداد CMS والتحقق من تطبيقه في استجابة التطبيق.

---

## المرحلة الخامسة: طلبات الاستغاثة (Blood Requests)
**الهدف**: بث الاستغاثة للمتبرعين القريبين.
**التقدير الزمني**: 1 أسبوع

- [ ] برمجة `POST /api/v1/blood-requests` لإنشاء طلب استغاثة.
- [ ] برمجة محرك البث: البحث عن المتبرعين المطابقين وإرسال FCM بدفعات.
- [ ] برمجة `PATCH /api/v1/blood-requests/:id/status` لتغيير حالة الطلب.
- [ ] تفعيل Rate Limiting على هذا الـ Endpoint (5 طلبات/دقيقة).

**اختبار المرحلة**:
- [ ] إنشاء طلب استغاثة والتحقق من وصول الإشعار للمتبرعين المطابقين.

---

## المرحلة السادسة: الاختبار والتدشين (Deployment)
**الهدف**: رفع الباكإند على السيرفر وتشغيله بشكل آمن.
**التقدير الزمني**: 1 أسبوع

- [ ] تشغيل `setup-server.sh` على السيرفر VPS.
- [ ] ضبط إعدادات PostgreSQL (shared_buffers, max_connections, work_mem).
- [ ] رفع الكود وضبط ملف `.env` على السيرفر.
- [ ] تشغيل `prisma migrate deploy` على قاعدة الإنتاج.
- [ ] تشغيل التطبيق عبر PM2.
- [ ] إعداد Nginx كـ Reverse Proxy مع HTTPS (Let's Encrypt).
- [ ] اختبار نهائي شامل من تطبيق الموبايل على السيرفر الحقيقي.
