# التدقيق الاستراتيجي والتحليل الفني المعمق (Strategic Audit)

هذا المستند يتناول أبعد من مجرد تحليل البيانات، بل يغوص في "المخاطر الخفية" والحلول الوقائية لضمان نجاح مشروع "نبض اليمن" على المدى الطويل.

---

## 1. تحليل مخاطر البنية التحتية (Infrastructure Risks)

### أ. هشاشة التنصيب المباشر (Bare-metal Fragility)
- **الإشكالية**: الاستغناء عن Docker يوفر الرام ولكنه يجعل السيرفر "صلباً" (Rigid). أي تحديث لنظام التشغيل قد يؤثر على الباكإند.
- **الحل المقترح**: توثيق "سكربت تجهيز السيرفر" (Setup Script) لضمان إمكانية إعادة بناء البيئة بسرعة.

### ب. سقف الموارد المشتركة (Shared Hardware Ceiling)
- **الإشكالية**: السيرفر يمتلك 4GB RAM ولكنه مخصص لعدة مشاريع (Laravel, Python وغيرها). استخدام Prisma دون قيود قد يؤدي لـ OOM (نفاد الذاكرة).
- **الحل المقترح**: تحديد سقف لبركة اتصالات قواعد البيانات (Connection Pool) الخاص بـ Prisma إلى 5 اتصالات متفرعة، وإنشاء فهرس GIST لتخفيف عبء معالجة (CPU) عمليات ST_DWithin.

---

## 2. تحليل هيكلية التطبيق الموحد (The All-in-One Risk)

### أ. مخاطر الثقة بالعميل (Client-Trust Logic Exposure)
- **الإشكالية**: دمج واجهات المشرف والمراكز الطبية داخل تطبيق الموبايل يجعله عرضة للهندسة العكسية.
- **الخطر الاستراتيجي**: كشف الـ Endpoints الخاصة بتعديل المخزون للمهاجمين.
- **الحل**: تفعيل الحماية على مستوى الـ API وضمان عدم إرسال بيانات إدارية إلا للأدوار المصرح لها (RBAC).

### ب. ثغرة "البحث الشعاعي" (Geospatial Reality vs Radius)
- **الإشكالية**: البحث الشعاعي (As the crow flies) يتجاهل وعورة التضاريس في اليمن والجبال.
- **الخطر**: متبرع قريب جغرافياً قد يكون بعيداً زمنياً.
- **الحل المقترح**: جعل مرشح "المديرية" (District) هو الأساس، مع خيار "البحث الشعاعي" كإضافة.

---

## 3. تحليل استراتيجية البث والإشعارات (Notification Architecture)

### أ. مخاطر الإرسال من طرف العميل (Client-side Security Risk)
- **النقد المنطقي**: الكود الحالي للفلاتر يحاول إرسال الإشعارات مباشرة باستخدام `serverKey` من الموبايل.
- **الخطر الكارثي**: كشف الـ `serverKey` يسمح لأي شخص بالتحكم في إشعارات التطبيق بالكامل.
- **الحل الجذري**: نقل صلاحية FCM بالكامل إلى السيرفر (NestJS) باستخدام `Firebase Admin SDK`.

### ب. منطق الاستغاثة الذكي وتنظيف التوكنات 
- **الإشكالية**: تراكم التوكنات המيتة للمستخدمين الذين حذفوا التطبيق سيرهق الشبكة الخادم.
- **الحل المقترح**: إضافة آلية لاصطياد خطأ `NotRegistered` من إجابات Firebase Admin SDK ومسح التوكن من خادم Postgres فوراً، مع تقسيم الإرسال إلى (Batches).

---

## 4. استراتيجية إصدارات الـ API (Versioning Strategy)

### أ. ضمان استمرارية الخدمة (Backward Compatibility)
- **الإشكالية**: تحديث الباكإند مستقبلاً قد يكسر الإصدارات القديمة من التطبيق.
- **الحل**: اعتماد URI Versioning (مثال: `/api/v1/...`) لضمان الانتقال السلس بين الإصدارات.

---

## 5. نقد الأداء (Performance Critique)

### أ. اختناق بروكسي الملفات (The Streaming Bottleneck)
- **الملاحظة**: جلب الصور عبر NestJS API للاعتماد على الـ UID سيزيد من استهلاك الذاكرة.
- **الحل المقترح**: استخدام **X-Accel-Redirect** في Nginx لتفريغ حمل البث عن نود.
