# 05 — قواعد التبرع والأهلية

## ما يفعله العميل / Firestore اليوم

| البند | الوضع |
|-------|--------|
| `eligible_until` على مستند المتبرع | حقل في Firestore — يُستخدم ضمنياً في البحث |
| تسجيل تبرع في المركز | غير واضح في UI القديم — قد يكون يدوياً |
| فلترة المتبرعين في البحث | جزء في العميل (`isShown`) + Firestore |

## ما يوفّره الباكإند اليوم

| Endpoint | السلوك |
|----------|--------|
| `GET /donor-search` | يستبعد `eligibleUntil` المستقبلي و `isShown=false` (**موجود**) |
| `POST /centers/me/donations` | يسجّل `Donation`، **يُحدَّث `eligibleUntil`** (الآن + `donation_cooldown_days`)، ويُرسل FCM شكراً للمتبرع (حتى 5 أجهزة) — [centers-and-inventory](../../backend_guide/api/centers-and-inventory.md) |

> **تصحيح توثيق سابق:** كان سطراً هنا يفترض «عدم التحديث التلقائي»؛ **عقد API الحالي** (والـ [implementation-status](../../backend_docs/implementation-status.md)) يقرّ بالتحديث — المصدر المعتبر هو `docs/backend_guide/api/`.

## متابعة — **تحقق إنتاج / عميل (P2)**

### 1. تطابق الإنتاج مع العقد

- [ ] تأكيد على بيئة الإنتاج أن `eligibleUntil` يتغيّر بعد `POST /centers/me/donations` كما في الدليل.
- [ ] `GET /donors/me` يعكس `eligibleUntil` فوراً بعد التبرع.
- [ ] `GET /donor-search` لا يعيد المتبرع خلال فترة الحظر.

**قاعدة الأعمال (للمرجع — من العقد، لا تكرار منطق في العميل):**

```text
بعد تبرع ناجٍ: eligibleUntil = now + N يوم، N من app-config donation_cooldown_days
```

### 2. إشعار المتبرع بعد التبرع — **موثّق في API؛ اختياري في العميل (P3)**

| مقترح | |
|--------|--|
| بعد `POST /centers/me/donations` | FCM من السيرفر للمتبرع — العميل **لا** يرسل |

يستخدم نفس بنية `/auth/device` — لا إرسال من العميل.

### 3. التحقق من هوية المتبرع عند التبرع — **جزئي**

المركز يمرّر `donorId` (رقم مستخدم API).

| مطلوب | |
|--------|--|
| التحقق أن `donorId` موجود و role=DONOR | |
| رفض 404/400 إن غير موجود | |
| اختياري: مسح QR يربط بـ `userId` لاحقاً |
